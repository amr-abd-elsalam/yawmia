# يوميّة — Data Migration Formats
> Phase 59 — Migration Snapshot Format for Phase 60+  
> Version target: v0.55.0

هذا الملف يحدد صيغة future migration snapshots.  
Phase 59 لا تستورد البيانات إلى أي external database.  
Phase 59 فقط تجهز snapshot format قابل للتحقق.

---

## 1. Snapshot directory layout

Example:

```text
migration-snapshots/2026-05-23T04-30-00/
  manifest.json
  users.ndjson
  jobs.ndjson
  applications.ndjson
  payments.ndjson
  messages.ndjson
  workrooms.ndjson
  notifications.ndjson
  audit.ndjson
  indexes/
    users-phone-index.json
    jobs-index.json
    applications-worker-index.json
    applications-job-index.json
```

Generated by:

```bash
node scripts/export-migration-snapshot.js --out=./migration-snapshots/test --confirm
```

Dry run:

```bash
node scripts/export-migration-snapshot.js --dry-run
```

    }

## 3. NDJSON collection files

Each line is one JSON object:

```json
{"id":"usr_abc","role":"worker","createdAt":"..."}
{"id":"usr_def","role":"employer","createdAt":"..."}
```

Rules:

```text
one JSON object per line
no trailing commas
UTF-8
no raw secrets
no raw session tokens
no raw identity image data
```

NDJSON is used because it is:

```text
streamable
easy to validate line-by-line
safe for large collections
friendly for future import tools
```

---

## 4. Checksums

If enabled:

```text
config.EXTERNALIZATION_READINESS.includeChecksums=true
```

Use SHA-256 per output file.

Manifest must include:

```text
sha256
count
sizeBytes
```

Checksums allow:

- snapshot integrity verification
- safe copy between machines
- rollback confidence
- Phase 60 import validation

---

## 5. Collection ordering

Recommended export order:

```text
users
jobs
applications
attendance
payments
ratings
reports
verifications
messages
workrooms
notifications
direct_offers
availability_ads
alerts
favorites
audit
ops_queue
governance records
metrics
```

Why:

- users referenced by almost everything.
- jobs referenced by applications/payments/messages.
- applications referenced by attendance/ratings.
- payments and disputes reference jobs/users.
- workrooms/messages need jobs and participants.
- audit can be preserved last.

## 6. Referential integrity notes

Important references:

```text
jobs.employerId -> users.id
applications.jobId -> jobs.id
applications.workerId -> users.id
attendance.jobId -> jobs.id
attendance.workerId -> users.id
payments.jobId -> jobs.id
ratings.jobId -> jobs.id
messages.jobId -> jobs.id
direct_offers.employerId -> users.id
direct_offers.workerId -> users.id
workrooms.jobId -> jobs.id
privacy_requests.userId -> users.id
```

Future import tools must validate missing references and produce a mismatch report.

---

## 7. Privacy / anonymization constraints

Migration snapshot must not include:

```text
ADMIN_TOKEN
session tokens
VAPID private key
webhook secrets
raw identity images
raw queue secrets
unrevealed third-party phone numbers
```

For sessions:

```text
Do not export raw session tokens by default.
```

For identity images:

```text
Export metadata refs only, not raw images, unless explicitly approved and encrypted in Phase 60+.
```

For user anonymization:

```text
anonymized users must remain anonymized in snapshots.
```

---

## 8. Image / object references

Images are stored by content hash.

Snapshot should include references:

```json
{
  "imageRef": "img_abcd1234",
  "purpose": "workroom_attachment"
}
```

Do not inline base64.

If Phase 60+ uses external object storage, image migration must be a separate controlled process.

---

## 9. Audit preservation

Audit records must be preserved when possible.

Rules:

```text
Do not blindly delete audit records.
Do not expose audit publicly.
Do not include secrets in audit details.
Keep adminId/targetId for governance unless anonymization policy requires redaction.
```

Audit index itself is rebuildable and does not need to be imported as source of truth.

---

## 10. Queue preservation options

Queue migration has two possible strategies:

### Option A — Drain before migration

Recommended for most deployments:

```bash
node scripts/queue-drain.js
node scripts/verify-queue.js
```

Then snapshot only completed/failed history if needed.

### Option B — Preserve queue state

Only if necessary:

```text
pending
running
failed
cancelled
dead-letter
idempotency
```

Pending jobs must remain idempotent after import.

## 11. Rollback snapshot notes

Before Phase 60 migration:

```bash
node scripts/export-migration-snapshot.js --out=./migration-snapshots/pre-phase60 --confirm
node scripts/backup.js
```

Rollback requires:

- snapshot manifest
- data backup
- version info
- migration logs
- repair scripts
- smoke test

## 12. Validation checklist

Before accepting a migration snapshot:

```bash
node scripts/verify-data-json.js --strict
node scripts/verify-file-health.js --strict
node scripts/verify-scale-thresholds.js --strict
node scripts/verify-queue.js
node scripts/verify-audit-index.js
node scripts/verify-workroom-indexes.js
node scripts/verify-privacy-governance.js --strict
```

Snapshot-specific validation:

```text
manifest exists
all NDJSON files parse line-by-line
counts match manifest
checksums match manifest
no session tokens exported
no raw identity image data
no raw secrets
referential integrity checked
```

---

## 13. What Phase 59 export script does

`scripts/export-migration-snapshot.js`:

```text
exports NDJSON
writes manifest
optionally includes checksums
respects YAWMIA_DATA_PATH
redacts/omits secrets
does not import anywhere
does not modify source data
```

---

## 14. What Phase 59 export script does NOT do

```text
Does not create PostgreSQL schema.
Does not connect to external DB.
Does not upload to external object storage.
Does not run dual-write.
Does not delete source data.
Does not bypass privacy rules.
```
